# Lai 家便當餐廳 AI OS 推進計畫
**日期**: 2026-08-26
**狀態**: Draft
**原則**: 先接住現場流程，再加 AI；AI 失敗時訂單、出餐、庫存不能停。

## 1. 現況基線
| 項目 | 現況 |
|---|---|
| 前台網站 | 已有 Lai 家便當公開頁、菜單頁、訂餐頁 |
| 訂單 API | 已有 `POST /api/orders`, `GET /api/orders`, status 更新 |
| 後台 | 已有接單工作台、查單、營業統計、列印設定、會員中心 |
| 資料儲存 | 有 PostgreSQL 與 local JSON 雙路徑 |
| POS | 有 webhook 設定與手動重送 |
| 列印 | 有網路印表機嘗試與檔案 fallback |
| 會員 | 手機當會員 key，完成訂單累點，支援手動兌換與送禮 |
| AI | 尚未接正式 AI 推薦、客服、報表 |

## 2. MVP 目標
MVP 交付「店內可用」而不是「功能展示」。完成後，一間店可以貼 QR，客人點餐，前台與後廚看到完整訂單，庫存不超賣，老闆每天看到營收/毛利/問題摘要。

### MVP 工作流
1. QR 點餐入口
2. 多語菜單與訂單欄位
3. 忌口/過敏標註
4. AI 推薦與加購，失敗可降級
5. 前台接單與例外確認
6. 後廚小票/看板顯示
7. 基本庫存與售完鎖定
8. 單品成本與每日毛利估算
9. 會員點數沿用與偏好紀錄
10. 客服回覆草稿與人工接手
11. 完成後評價邀請
12. 每日老闆報表

## 3. Phase 2 目標
Phase 2 將 OS 從「可營運」提升為「可管理」。重點是資料品質、異常流程與可回溯。

- 食材 BOM 扣庫。
- AI 翻譯草稿與人工發布流程。
- 會員偏好與回訪券。
- 缺貨替代建議。
- 客服渠道整合，例如 LINE OA 或 Google 商家訊息。
- 負評預警與補償紀錄。
- 同比/環比報表、食材耗用、尖峰時段分析。
- 權限與操作紀錄。

## 4. Phase 3 目標
Phase 3 將 OS 擴到「預測與多店」。任何自動化仍需要 Gate 與人工覆核。

- 多店菜單、價格、庫存與報表控管。
- 需求預測與備料建議。
- 自動採購建議與供應商比較。
- 個人化套餐與分群行銷。
- 廚房排程最佳化。
- AI 經營建議與調價模擬。
- 多渠道客服品質評分。

## 5. 里程碑
| 里程碑 | 階段 | 交付物 | 完成定義 |
|---|---|---|---|
| M0 現況鎖定 | MVP | 現有 API/頁面/資料表盤點 | `spec.md` 與 `agent-map.md` 對得上現有系統 |
| M1 QR 訂單資料擴充 | MVP | source/table/language/dietary/allergy 欄位 | 新訂單能保存並在後台顯示 |
| M2 多語菜單 | MVP | 繁中/英文/日文/韓文文案資料 | 缺翻譯時回退繁中 |
| M3 AI 推薦 Gate | MVP | AI 推薦服務契約與 fallback | AI 逾時不阻斷結帳 |
| M4 前台/後廚例外流 | MVP | 忌口/過敏/缺貨/重複單標記 | 前台可辨識高風險單 |
| M5 庫存與成本 | MVP | 可售量、預扣、回補、成本快照 | 不超賣，日報可估毛利 |
| M6 客服/評價/報表 | MVP | 回覆草稿、評價邀請、每日報表 | 打烊後可產出老闆摘要 |
| M7 Phase 2 擴充 | Phase 2 | BOM、渠道、權限、負評流程 | 每個分支有測試案例 |
| M8 Phase 3 多店預測 | Phase 3 | 多店與預測模組 | 自動建議不自動執行 |

## 6. MVP 實作順序
| 順序 | 工作 | 依賴 | 風險控制 |
|---|---|---|---|
| 1 | 擴充訂單資料 contract | 現有 `/api/orders` | 保持舊訂單可讀 |
| 2 | QR 入口參數與語言回退 | 訂單頁 | 沒 QR 仍可一般點餐 |
| 3 | 菜單資料補 tags/translations | catalog/order 菜單來源 | 未標過敏的品項不可做 AI 推薦 |
| 4 | 忌口/過敏 UI 與後台顯示 | 訂單 contract | 高風險單預設要求人工確認 |
| 5 | 庫存預扣/回補 | 訂單狀態流 | 狀態轉移必須冪等 |
| 6 | AI 推薦 | 菜單+庫存+會員 | 3 秒 timeout，失敗即略過 |
| 7 | 成本快照與日報 | 訂單+成本資料 | 成本缺漏時標示未知，不亂算 |
| 8 | 客服草稿/評價邀請 | 訂單完成流 | 食安/過敏/退款不得自動回覆 |

## 7. 營運導入計畫
| 天數 | 店內動作 | 系統動作 |
|---|---|---|
| D-7 | 確認菜單、售價、過敏原、成本 | 建立 MVP 菜單資料 |
| D-5 | 確認 QR 貼紙位置與桌號命名 | 產生 QR 測試連結 |
| D-3 | 前台/後廚教育訓練 | 測試接單、拒單、列印、缺貨 |
| D-1 | 試營運半天 | 開啟監控與手動備援流程 |
| D0 | 正式上線 | 啟用 Gate 通過的外部服務 |
| D+1 | 檢討日報與客訴 | 修正菜單、文案、庫存閾值 |

## 8. 失敗降級策略
| 故障 | 降級方式 |
|---|---|
| AI API 失敗 | 不顯示推薦；客服/報表改規則版 |
| POS webhook 失敗 | 訂單照收；標記 failed，前台手動重送 |
| 印表機失敗 | 產生小票檔；後廚用看板或手抄 |
| PostgreSQL 失敗 | 若正式營運不得自動切 local JSON，需進入維護或人工接單 |
| 翻譯缺漏 | 回退繁中 |
| 庫存資料缺漏 | 禁用自動售完，前台人工確認 |

## 9. 測試策略
- API 測試: 訂單建立、驗證失敗、庫存衝突、狀態轉移、點數只發一次。
- UI 測試: QR 參數、多語切換、過敏標示、加購接受/略過、送出成功/失敗。
- 營運測試: 前台接單、後廚出餐、列印 fallback、POS 重送。
- 報表測試: 有 AI key、無 AI key、成本缺漏、負評/客訴存在。
- 併發測試: 同一品項最後 1 份被兩位客人同時下單。

## 10. 決策點
| 決策 | 建議 |
|---|---|
| MVP 庫存粒度 | 先用「單品可售份數」，Phase 2 再 BOM 食材 |
| AI 供應商 | 先支援 OpenAI-compatible contract，保留 provider 替換 |
| 客服渠道 | 先後台草稿與人工貼上，Phase 2 接 LINE OA |
| 評價渠道 | 先生成 Google 評價或自家表單連結，Phase 2 做整合 |
| 報表收件 | 先後台頁面與可複製摘要，Phase 2 推 LINE/Email |
